# Agent rules — entry points and scope

Updated: 2026-08-30. For this repository read [AGENTS.md](../../AGENTS.md) and [project rules](REPOSITORY_RULES.md) first. They supersede conflicting historical public-site agent instructions.

- Public-site tasks come only from the [canonical roadmap](../roadmaps/ASDEV_PUBLIC_EXPERIENCE_EXECUTION.md); [sprint cards](../execution/V3_2_AGENT_SPRINTS.md) define complete outcomes.
- Follow the [engineering guide](../engineering/PUBLIC_EXPERIENCE_ENGINEERING.md) for actual stack, libraries, performance, safety and available skills. Detect tools/paths; do not assume a model, host, Windows path or paid service.
- ORCH alone integrates and updates the [ledger](../execution/V3_2_WORK_LEDGER.md). No mandatory parallel queue, broad memory rewrite, registry edit or unrequested external post for every public-site task.
- Use isolated branches/worktrees, inspect full ancestry/diff and preserve dirty owner work. No force-push/bypass. Normal eligible PR merges follow live rules; do not invent a human-approval gate.
- Continue safe dependency-ready work automatically. Keep existing valid authorizations within scope; [approval gates](APPROVAL_GATES.md) still govern actual runtime/data actions. A file containing a token does not authorize deployment.
- Check [report review protocol](CODEX_REPORT_REVIEW.md) before accepting any completion report. Source, visual, motion, accessibility, performance and release evidence are different dimensions. Missing proof is not PASS.
- No secrets, data loss, unsupported metrics, fake tests/screenshots/reviews, production fixture writes, unrelated refactors or implicit database migration.

Ecosystem policies remain applicable to their original work. They cannot redirect this admitted public-experience mission to a competing roadmap or invent activity after it is complete.
